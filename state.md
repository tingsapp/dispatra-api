# Dispatra API implementation state

Updated: 2026-09-29. [Specification](spec.md) defines the product contract; [README](README.md) describes the runnable service.

## Implemented

- PostgreSQL with forced tenant row security, restricted runtime role, account and session boundaries, versioned writes, idempotency, audit records, and transactional outbox. Persistent demo accounts and pricing are seeded separately from disposable test data.
- Company settings; catalogues and Rate Cards; Shipper, Driver and Vehicle profiles; account creation with one-time generated password; safe archive commands; and Shipper self-service contact, phone and warehouse updates. Dispatcher Driver edits now save On/Off duty atomically without granting GPS permission or recording location.
- Shared dispatcher/Shipper booking, prospect Quotes, API pricing review, immutable pricing snapshots, Order revisions, assignment and release, bounded route optimization, route execution, driver duty/telemetry, evidence and proof of delivery, verified completion, Invoice issuance, and explicit Quote/Invoice email queueing.
- API-backed Monitor, dated Analytics/CSV, Driver Activity & Earnings, booking preferences, delivery proof and role-scoped portal projections. Monitor reports actual duty state and stored route/Order attention. Analytics uses dated stored records rather than browser samples.
- Google road routing is available for explicit pricing/planning calls when configured; local demo routing remains available without provider calls. The API keeps operational addresses structured; selected Google Places components can be stored directly, including city, province, postal code, country and coordinates.

Public entity references for Orders, Drivers, Shippers and Vehicles now use company-initial codes (for example `DCO-1234`). Vehicle public numbers are separate from fleet Unit numbers; internal UUID relationships remain unchanged. Migration `0012_public_entity_numbers` backfills existing operational records.

Shipper driver preference and rate card (2026-09-29): `Booking.preferred_driver_id` is optional and must name an active, unarchived company Driver when set or changed (422 otherwise); unchanged values survive dispatcher edits even if the driver is later archived. It never assigns and does not affect pricing. `GET /booking-drivers` (dispatcher or shipper) returns only id and name of active Drivers; because forced RLS hides drivers from shipper sessions, the read briefly switches to company scope for that explicit projection and restores the session context. `ShipperView.rate_card_name` names the card that prices the shipper (its own, else the company Default), and saving a Shipper without a Rate Card stores the Default. No migration: the preference lives in Order `facts`. Verification: the full suite passed (62 tests, including `test_shipper_preferred_driver_and_rate_card`); OpenAPI exported and the client schema regenerated.

Booking preferences (2026-09-29): `/booking-preferences` also returns `gst_enabled`, `gst_percent`, `provincial_enabled`, `provincial_percent`, `fuel_enabled` and `fuel_percent` from company settings so the Shipper estimate displays the live terms. Verification: targeted shipper tests plus `test_client_contract.py` and `test_edge_cases.py` passed; OpenAPI exported.

Road distance and duration (2026-09-29): `travel.order_travel` replaces `order_distance` and requests `routes.distanceMeters,routes.duration` in one call, returning km (2 dp, half-up) and driving minutes (ceiling). `price_context` calls it for BASE_PLUS_DISTANCE without distance or HOURLY without minutes; missing minutes become driving time plus each stop's `service_minutes`, and `calculate` applies both from the frozen context. The local `api/.env` now uses `ROUTING_PROVIDER=google` (billable Routes calls on pricing). Stops without coordinates still return 409 "Verified stop coordinates are required for road routing"; the seeded demo Shipper warehouse "123 Demo Street" has none. Verification: the full suite passed (63 tests, after widening the pinned `/booking-preferences` field set in `test_web_projections_quotes_and_stop_issue_scope` for the tax/fuel fields), including a mocked Routes response test, and a live dispatcher preview with Google-selected stops priced the Distance based card ($53.97, 3 km, 29 min).

Order road path (2026-09-29): `GET /orders/{id}/road-path` (dispatcher) returns decoded `routes.polyline.encodedPolyline` points from one Routes call through the Order's stops in precedence order; `order_route` is shared with `order_travel`. Demo routing or stops without coordinates return 409. Verification: `tests/test_pricing_and_routing.py` passed (6 tests, including decoding Google's documented sample polyline with a mocked response); live call returned the path for DDO-9450.

## Boundaries

Inbound email intake, AI agents, automatic dispatch/invoicing, Stripe collection, payroll, push delivery, native background tracking and durable offline client queues are not implemented in this manual phase. Road provider responses are not persistently cached. Evidence images are stored in PostgreSQL pending object-storage and retention work. An issued Invoice is not automatically emailed or paid; explicit sends queue email, and recipient delivery has not been verified. Partial quantity or failed delivery remains an issue requiring dispatcher resolution; full recovery/rebooking is not implemented.

The original client layouts are retained and now use these operational endpoints in company workspaces and role portals. `/prototype` is the separate local simulation. Browser demo records are not imported into PostgreSQL automatically.
